# 리치 선물 레이더 서버 실행 모듈

상태: 개발·로컬 테스트 단계. 서버 배포 및 실제 Telegram 수신 확인 전에는 운영 중이 아닙니다.

## 기존 시스템과의 관계

기존 웹사이트, Upbit Worker, D1, 정보 수집 Cron은 그대로 유지합니다.
`assets/futures-engine.js`의 마크가격/OI 응답 검증과 15분 OI 계산을 재사용합니다.
별도 Node 22 프로세스가 브라우저 없이 실행됩니다. 거래 주문/API 키는 사용하지 않습니다.

2026-10-13 18:49 KST 기존 Worker `/debug/reachability` 점검에서 Binance Futures HTTP 403,
Upbit HTTP 200을 확인했습니다. 따라서 기존 Cloudflare Cron에 Binance 호출만 붙여서는
작동하지 않습니다. 서비스 이용 조건에 맞으며 공식 API 접속이 허용된 실행 환경이 필요합니다.
차단 시 프록시/미러/우회 없이 수집 장애로 처리합니다.

## 현재 구현

- 5분 경계 직후 감시, 정각 이후 첫 정상 주기에 시간당 보고 1회.
- 실제 TRADING USDT 무기한 계약만 선택. BTC/ETH 및 24시간 거래대금 상위 최대 12종목.
- 완료된 5분봉만 사용. 직전 20봉 고저점 돌파, 12/48봉 단순평균 방향, 거래대금 2배,
  15분 OI +1% 이상, 펀딩 절댓값 0.05% 이하, 기준선과 마크가격 거리 1 ATR 이내를 모두 확인.
- BTC 15분 변동이 반대 방향 0.5%를 넘거나 BTC 데이터가 없으면 강한 신호 차단.
- 기준선과 14봉 ATR 기반 무효화 참고선을 숫자로 표시. 지지/저항 재확인은 사용자가 해야 하며
  자동 진입 신호나 백테스트로 검증된 수익 확률이 아닙니다.
- 시간당 보고 상위 2개, 시간 사이 신규 조건 최대 2개. 종목/방향별 1시간 중복 억제.
- 캔들 누락, 가격/OI 지연, 펀딩 미확인 시 해당 종목 제외. 전체 실패 시 가격을 만들지 않고 장애 알림.
- 403/451은 1시간 대기, 429는 Retry-After 준수. Telegram 전송 성공 이후만 기록.
- 재시작 후 상태 유지, 단일 프로세스로 중첩 실행 방지. Telegram 전송 직후 저장 전 강제 종료되면
  1회 중복 가능(외부 API에 idempotency key 없음). 복수 인스턴스 실행 금지.
- 첫 버전은 규칙 기반 수치 분석입니다. LLM 분석·뉴스 원인 연결은 아직 구현하지 않았습니다.

## 운영 전 필요한 검증

1. 승인된 상시 실행 서버에서 `RADAR_STATE_DIR=/tmp/radar-preview node radar-service/run.mjs --preview`.
   공식 Binance API 수집 성공, 현재 가격/시각 확인. 프리뷰는 Telegram 전송/운영 상태 저장 없음.
2. 기존 봇의 비밀 토큰을 서버 비밀 환경에 설정하고 수신자가 소유자의 개인 chat ID인지 확인.
   토큰을 GitHub, 보고서, 채팅 또는 로그에 쓰지 않기.
3. 저장소 루트 기준 `docker compose -f radar-service/compose.yaml up -d --build`.
   `.env.example`은 안내용이며 실제 `.env`는 커밋 금지.
4. 시간당 보고 실수신, 강한 조건 알림, 서버 재시작 후 중복 억제, 장애 알림 확인.

운영 상태는 영구 볼륨 `/data/state.json`에서 lastAttempt/lastSuccess/lastError를 확인합니다.
봇 토큰·chat ID는 상태 파일에 저장하지 않습니다. 중단은 compose stop으로 가능합니다.
새 서버 생성/유료 계약/Telegram 비밀값 설정은 아직 수행하지 않았습니다.

  (3) 무료 티어이면서 허용 지역 리전을 선택할 수 있는 실행 환경을 사용자가 약관 확인 후 직접 선택.


## 2026-10-13 데이터 출처 변경: OKX (Binance 아님)

GitHub Actions 러너(ubuntu-24.04)에서 BTC/ETH/SOL 기준 실제 응답 검증 (`radar-service/probe-exchanges.mjs`):

| 거래소 | 결과 |
|---|---|
| Bybit v5 | HTTP 403 (0/9 유효) — 지역 차단, 사용 불가 |
| OKX v5 | HTTP 200, 18/18 유효. code "0" + 유효 가격·마크가격·5분봉·OI·OI 5분 이력·펀딩 확인, 응답 약 110~270ms |

- 기본 데이터 출처는 OKX USDT 무기한(SWAP). 모든 보고서에 "OKX · Binance 데이터 아님"을 표시합니다.
  Binance 가격으로 표기하지 않으며, 접근 가능한 네트워크에서만 `RADAR_SOURCE=binance`로 선택할 수 있습니다.
- 확정(confirm=1) 5분봉만 사용. OI는 기초자산 수량(oiCcy) 기준 15분 변화율. 거래대금은 직전 20봉 평균 대비 비율.
  24시간 거래대금은 종목 순위용 근사치(기초자산 24h 수량 × 최근가).
- OKX 호출 한도 준수를 위해 호출 간 260ms 간격. 12종목 수집 약 25초.
- 안전형/공격형: 강한 조건 중 BTC가 같은 방향이고 |펀딩| ≤ 0.02%, 15분 OI ≤ 5%, 기준선 이격 ≤ 0.5 ATR이면 안전형, 아니면 공격형.
  규칙 분류일 뿐 수익률·승률과 무관합니다.

### GitHub Actions 운영 (`.github/workflows/radar.yml`)

- 5분 cron + 수동 실행. 공개 저장소 표준 러너는 무료. 스케줄은 `main` 브랜치 워크플로만 실행됩니다.
- GitHub 스케줄은 수 분~수십 분 지연되거나 건너뛸 수 있어 정확한 5분 감시/정시 보고는 보장되지 않습니다.
  시간당 보고는 "새 시간대의 첫 정상 실행"에서 1회 전송됩니다.
- 상태(중복 억제·보고 시각)는 Actions 캐시(`.radar-state`)로 실행 간 보존. 캐시가 사라지면 보고 1회가 중복될 수 있습니다.
- 60일간 저장소 활동이 없으면 GitHub가 스케줄을 자동 중지합니다.
- 필요한 저장소 비밀값(Settings → Secrets and variables → Actions): `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`(개인 chat ID).
  미설정 시 수집·분석 결과만 로그에 출력하고 전송하지 않습니다.

### 계산식
- **추세(15분·1시간·4시간, 확정 캔들만)**: 스윙 고점/저점(양옆 2봉 기준)의 직전 대비 상승(+1)/하락(-1), MA10·MA30·종가 정렬(+1/-1/0)의 합이 ≥2 상승, ≤-2 하락, 그 외 횡보. 30봉 미만·캔들 누락·수집 실패는 미확인.
- **점수(100점)**: 다중 시간대 20(15분 6·1시간 7·4시간 7, 동일방향 만점/횡보 절반/역행·미확인 0) · 돌파·가격 구조 20(확정 돌파 20, 미돌파는 기준선까지 0.25/0.5/1/2 ATR이면 16/12/8/4, 5분 추세가 반대면 절반) ·
  거래대금 15(직전 20봉 평균 대비 0.8배 0점 → 2배 만점) · OI 15(15분 변화 0% → +1% 선형) · 펀딩 10(|펀딩| 0.01% 이하 만점 → 0.05% 0점) ·
  BTC 필터 10(BTC 15분이 같은 방향 ≥0.1% 10 · ±0.1% 7 · 0.5% 이내 역행 3 · 초과 0) · 변동성·이격 10(기준선 이격 0.5/1/2 ATR이면 5/3/1 + ATR% 0.5/1/2/3 이하면 5/4/2/1).
  결측 항목은 0점이며 `데이터 누락`에 표시합니다. 점수는 조건 충족도이며 승률·수익 확률이 아닙니다. 뉴스는 점수에 넣지 않습니다.
- **필수 차단(점수 무관)**: BTC 데이터 없음, BTC 15분이 후보 반대 방향으로 0.5% 초과. 차단되면 strong 아님·근접 후보 제외.
- **근접 후보**: strong이 아니고 차단 없음·점수 40 이상·돌파 기준선까지 2 ATR 이내인 종목을 점수순 최대 3개. 조건에 맞는 것만 출력하고 채우지 않습니다. 근접 후보는 정기 보고에만 포함(긴급 알림 없음).
- **시나리오**: 진입=이미 기준선 돌파면 현재 마크가격, 아니면 기준선(조건부 진입 참고가). 손절=롱 `min(기준선-1ATR, 최근 12봉 저점-0.1ATR)`, 숏은 반대. R=|진입-손절|, TP1=진입±1R, TP2=진입±2R(손익비 1:1·1:2).
  1시간 스윙 구조가 TP1보다 가까우면 표시. 손절 거리 8% 초과 또는 방향 검증 실패 시 숫자를 만들지 않고 "계산 불가". 수수료·슬리피지·펀딩비 미반영. 강제청산가는 증거금·포지션 데이터가 없어 "확인 불가".
- **위험 수준**: 4시간 역행 +2, 1시간 역행 +1, 시간대 미확인 +1, BTC 충돌 +2~3, OI 15분 ≥3% +1(감소도 +1), 펀딩 >0.03% +1·>0.05% +2, ATR >1.5% +1·>2.5% +2, 거래대금 <1배 +1, 기준선 이격 >1ATR +1, 손절 거리 >2% +1·>3% +2, 1H 구조가 TP1보다 가까움 +1, 시나리오 계산 불가 +1, 가격 지연 +1. 0~1 낮음 · 2~4 보통 · 5 이상 높음. "낮음"도 안전이나 수익 보장이 아닙니다.
  "보수형"은 상대적으로 보수적인 조건(이전 "안전형")이라는 뜻일 뿐입니다.
- **시장 상태**: BTC 1시간·4시간이 모두 상승이면 상승, 모두 하락이면 하락, 그 외 혼조, 미확인이면 판단불가.

## RICH FUTURES RADAR 2.3 — 추천 관찰 TOP 2 + 거래량·추정 매물대 차트 (브랜치 `feature/radar-2-3`)

분석 엔진(수집·점수·시나리오·리스크·뉴스)은 그대로입니다. 출력만 확장했고 **추가 OKX API 호출은 0회**입니다(기존 캔들 응답 재사용).

### 추천 관찰 후보 TOP 2 (`scoring.pickTop2`)
1. 강한 관찰 조건을 충족한 종목(조건 충족 점수 높은 순) → 2. 근접 후보를 **순위값 = 점수 − 2 × 위험 점수**가 높은 순으로 → 같은 종목은 1회만.
   BTC 필터·필수 차단 조건을 유지하고(차단된 종목 제외), 근접 후보의 기존 자격(점수 ≥ 40, 기준선까지 2 ATR 이내)도 그대로입니다. 적격 후보가 부족하면 1개 또는 0개만 보여주며 숫자를 채우지 않습니다.
   롱·숏 구성을 강제하지 않습니다(둘 다 롱/숏 가능). 표시 점수는 조건 충족도이며 성공 확률이 아니고, "추천 관찰 후보"는 매매 지시가 아닙니다.
- 첫 메시지(`compact.mjs`): 후보마다 순위·종목·방향·점수·강한 신호/조건 미완성, 현재가·진입 기준·손절·목표(TP1/TP2), 확인 조건 ≤2, 주의 ≤2. 보이는 글자 800자 이내(보통 450~500자), 뉴스는 최대 1건(필요하면 생략).
- 전송 순서: 텍스트 1개 → 1순위 차트 → 2순위 차트. 후보가 0개면 BTC 4시간 시장 차트 1장(진입 가격 없음).

### 거래량 (OKX 캔들 필드 단위)
`/market/candles` 행: `[ts, o, h, l, c, vol, volCcy, volCcyQuote, confirm]`
- `vol` = **계약 수량**(거래대금 아님, 사용하지 않음), `volCcy` = 기초자산 수량, `volCcyQuote` = **USDT 거래대금 → 차트·매물대에 사용**.
- 단위 점검: 한 캔들의 `volCcyQuote / volCcy`(평균 체결가)가 [저가, 고가] ±2% 안에 있어야 정상이며, 벗어나거나 한쪽만 0이거나 NaN·음수·누락이면 그 캔들의 거래량은 `null`(비정상)으로 두고 보정하지 않습니다. 둘 다 0이면 0(무거래 봉).
- 5분·15분·1시간·4시간 캔들 모두 같은 규칙으로 `q`(USDT)와 `v`(기초자산)를 붙입니다(검증을 통과한 캔들만 차트에 사용).
- 차트의 거래량 패널: 봉별 막대(상승 청록·하락 붉은색), **직전 20봉 평균선**(현재 봉 제외, 유효 10개 이상일 때), 평균의 2배 이상은 **급증**으로 굵은 테두리. 유효 봉이 70% 미만이면 "거래량 데이터 부족"으로 표시하고 거래량·매물대를 그리지 않습니다.

### 추정 매물대(Volume Profile)와 POC — 계산식과 한계
- 표시 중인 최근 48개 확정 캔들, 가격 범위 [최저 저가, 최고 고가]를 24구간으로 균등 분할.
- 캔들마다 USDT 거래대금 `q`를 **[저가, 고가] 범위에 균등 분포한다고 가정**하고, 각 구간과 겹치는 길이 비율만큼 배분합니다: `구간 i 몫 = q × 겹침길이(i) / (고가 − 저가)`. 고가 = 저가인 캔들은 그 가격이 속한 구간에 전액 배분. 합계는 보존됩니다(테스트로 검증).
- **POC** = 배분 합이 가장 큰 구간(동률이면 현재가에 가까운 구간, 그래도 같으면 낮은 구간). **관찰 구간**은 POC와, 3구간 이상 떨어져 있고 사이에 골짜기(자기 거래대금의 80% 이하)가 있으며 POC의 50% 이상인 봉우리 최대 1개, 양옆 최대 2구간까지 묶어 최대 2개.
- **한계**: OHLC 캔들에는 개별 체결 가격이 없어 실제 체결 매물대를 복원할 수 없습니다. 이 값은 캔들 범위 기반 **추정**이며 실제 호가 잔량이 아닙니다. POC·관찰 구간은 강한 지지/저항으로 단정하지 않는 관찰 가격이고, **점수에는 반영하지 않습니다**(실전 효과를 검증하기 전까지 시각 보조지표).
- 차트 푸터에 "캔들 거래량 기반 추정 매물대 · 실제 호가 잔량 아님"을 항상 표시합니다.

- 사진 하나가 실패해도 다른 사진과 텍스트는 정상이며, 사진 실패로 텍스트를 다시 보내지 않습니다(사진 업로드 재시도는 1회, 429/4xx는 즉시 포기). 긴급 강한 신호는 기존처럼 해당 종목 텍스트 + 차트 1장만 보냅니다.


### 추천 표시 기준 55점 (2.3 패치)
- 내부 근접 후보 감시 하한 `NEAR_MIN_SCORE = 40`은 그대로이고, **정기 보고 추천 TOP 2에만** `RECOMMEND_MIN_SCORE = 55`(조건 충족 점수 기준)를 적용합니다. `pickNear()`는 기존 규칙, 표시용 하한은 `pickTop2()`에만 있습니다.
- 40~54.9점 근접 후보는 내부 계산·위험 분석·상태 기록(`state.rows`)에 그대로 남고 보고·차트에서만 빠집니다. 55점은 점수 기준이며 `rankValue`(= 점수 − 2×위험 점수)가 아닙니다. 적격 후보 사이의 정렬만 `rankValue`를 씁니다.
- 정기 TOP 2의 strong 후보에도 55점을 적용하지만, strong 판정과 5분 긴급 알림은 이 기준으로 억제하지 않습니다(정기 추천 표시와 실시간 탐지는 별개).
- 텍스트와 차트는 같은 `pickTop2()` 결과를 공유합니다. 추천 0개면 "⏳ 현재 추천 표시 기준(55점)을 충족한 후보 없음"을 표시하고, 내부 감시 후보가 있으면 "내부 감시 중인 근접 후보 n건 (55점 미만 · 표시 안 함)"을 덧붙입니다. 이때 차트는 BTC 시장 차트 1장(가짜 진입·손절·목표 없음)입니다.
