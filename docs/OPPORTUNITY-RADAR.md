# 기회 포착 레이더 (관찰 알림)

> **이 기능은 매매 신호가 아니다.** 사용자가 관심을 가질 만한 차트 조건(4시간봉 추세 + 1시간봉 지지·저항 접근/눌림/재진입 확인)을 충족하는 코인을 골라 Telegram으로 알리는 *관찰 알림*이다.
> 같은 조건 구조는 연구(PR #24~#26)에서 **수익성 검증 기준을 통과하지 못했다**(비용 반영 기대값이 0을 유의하게 넘지 않았고 무작위 진입과 구별되지 않음). 그래서 이 기능은 수익률·승률·진입 가격을 말하지 않고, 알림마다 "수익성은 검증되지 않았다"고 명시한다.
> 기능 플래그 `RADAR_OPPORTUNITY` 기본값은 **off**이며, 켜는 것은 사용자의 별도 승인 사항이다. 실거래 주문·자동 진입·레버리지 추천은 구현하지 않았다.

## 1. 무엇을 하나

코인(OKX USDT 무기한, 24시간 거래대금 상위 20종목 + BTC, `RADAR_OPPORTUNITY_TOP`로 최대 30)마다 매 정시 직후 한 번 점검한다.

| 상태 | 뜻 |
|---|---|
| **LONG 관찰** | 4H 상승 추세에서 지지 구간 쪽 조건을 점검 중 (매수 권고 아님) |
| **SHORT 관찰** | 4H 하락 추세에서 저항 구간 쪽 조건을 점검 중 (매도 권고 아님) |
| **대기** | 추세가 혼조이거나 가까운 지지·저항 구간이 없음 |

관찰 상태는 단계로 나뉜다(전체 충족이 아니어도 '관찰 중'으로 표시).

| 단계 | 이름 | 조건 |
|---|---|---|
| 1 | 구간 접근 중 | 추세 방향이 분명하고 가격이 지지(저항) 구간 위(아래) 1.5 ATR(4H) 이내로 접근, 아직 닿지 않음 |
| 2 | 눌림 진행 중 | 최근 12시간 안에 구간에 닿았고 1H 종가가 구간을 이탈하지 않음. 다른 조건 일부 미충족 |
| 3 | 조건 충족 | 아래 7개 점검 항목이 모두 충족 |

**Telegram 알림은 기본적으로 2단계(눌림 진행 중) 이상부터 보낸다.** 1단계(구간 접근 중)는 `state.opportunity`에 기록만 하고 알리지 않는다(`RADAR_OPPORTUNITY_MIN_STAGE=1`로 바꾸면 알림). 3단계(조건 충족)는 모든 상한·정렬에서 최우선이다.

점검 항목 7개 (충족 개수 n/7은 **설명용**이며 확률·승률이 아니다):
1. 4H 추세: 상승 = EMA50 > EMA200, 종가 > EMA200, 확정 스윙 HH·HL / 하락은 대칭
2. 지지(저항) 구간 접촉: 4H 스윙 저점(고점) 또는 돌파 후 역할이 바뀐 구간(폭 ±0.3 ATR(4H))에 최근 12시간 안에 접촉
3. 구간 유지: 그 12시간 동안 1H 종가가 구간을 이탈하지 않고, 구간 밖에서 내려온 눌림일 것
4. 재진입 확인 캔들: 양봉(음봉) 마감 + 직전 종가 상회(하회) + 구간 회복(복귀)
5. 추격 아님: 구간에서 1.0 ATR(4H) 이내, 마지막 봉 고저 폭 2.0 ATR(1H) 이하
6. 무효화 거리 적정: 무효화 가격까지 1.0~3.5 ATR(1H)
7. 반대편 공간: 가장 가까운 반대편 저항(지지)까지 2R 이상(무효화 거리 기준)

함께 표시하는 참고 지표: BTC 4H 추세(EMA 정렬, 일치/역방향/중립), 상대 거래량(마지막 1H 거래대금 ÷ 직전 20봉 평균), 변동성(ATR 1H·4H의 % — 4H ATR 1.5% 미만 낮음 / 3.5% 미만 보통 / 이상 높음), 추격 위험(구간 이격과 봉 폭 기준 낮음/보통/높음). 이 값들은 설명용이며 상태 판정에는 앞의 7개 항목만 쓴다.

- **참고 가격**: 마지막으로 마감된 1H 종가. 주문 가격이 아니다.
- **무효화 가격**: min(눌림 12봉 최저가, 구간 하단) − 0.5 ATR(1H) (SHORT는 대칭). 1H 종가가 이 가격을 이탈하면 관찰을 해제한다.
- 모든 임계값은 연구 문서(`TREND-PULLBACK-4-0-PREREG.md`)의 규칙에서 가져온 고정값이며 이 기능을 위해 최적화하지 않았다.
- 인기 지표(Supertrend, RSI, MACD)는 쓰지 않는다.

## 2. 알림 규칙 (중복 제한 · 우선순위 · 상한 · 첫 실행)

코인마다 *관찰 에피소드*를 추적한다(`radar-service/opportunity/transition.mjs`).

| 상황 | 동작 |
|---|---|
| 대기 → 관찰 시작, 단계 ≥ 2 | 알림 ("새 관찰") |
| 대기 → 1단계(구간 접근) | **기록만, 알리지 않음** (MIN_STAGE=1이면 알림) |
| 같은 에피소드에서 단계 상승 (눌림 → 조건 충족) | 알림 ("단계 상승") |
| 같은 단계 유지, 단계 하락 후 이미 알린 단계로 재상승 | **알리지 않음** |
| 방향 전환 (LONG ↔ SHORT) | 알림 (쿨다운 예외). 새 방향이 알림 단계 미만이면 이전 방향의 해제만 알림 |
| 1H 종가가 무효화 가격 이탈 | 즉시 해제 알림 |
| 대기로 복귀 | 연속 2개 마감 1H 봉에서 확인되면 해제 알림 (한 번의 깜빡임은 무시) |
| 해제 후 재발생 | 새 에피소드. 같은 코인의 알림 간격은 2시간 이상 (조건 충족은 예외) |
| 알린 적 없는 관찰(1단계만 있었거나 첫 실행 silent 기준선)의 종료 | 조용히 종료 |

**우선순위**(`priority.mjs`) — 상한을 적용하기 *전에* 정렬한다: ① 조건 충족(3단계, 새 관찰·단계 상승·방향 전환 포함) → ② 무효화 이탈 해제 → ③ 방향 전환(3단계 미만) → ④ 눌림 진행 중 → ⑤ 일반 해제 → ⑥ 구간 접근. 같은 순위에서는 충족 개수 많은 순 → BTC 4H 일치 → 종목명(결정적 순서).

**상한**(모두 `state.opportunity`에 기록, 초과분은 *보류*하고 다음 점검에서 다시 평가한다 — 잃어버리지 않음)
| 항목 | 기본값 | 변수 |
|---|---|---|
| 시간당(UTC 정시 기준) 최대 알림 코인 수 | 12 | `RADAR_OPPORTUNITY_MAX_PER_HOUR` (1~30) |
| 일일(UTC 날짜 기준) 최대 알림 코인 수 | 80 | `RADAR_OPPORTUNITY_MAX_PER_DAY` (1~200) |
| 조건 충족(3단계)을 위한 시간당 예비 칸 | 3 (상한이 작으면 상한/4) | 고정 — 눌림 단계 알림은 시간당 9칸까지만 쓰므로 조건 충족이 늦게 나와도 자리가 남는다 |

**발송량 기록**: `state.opportunity.sent`(이번 시간대 코인·조건 충족·메시지 수)와 `state.opportunity.daily[YYYY-MM-DD]`(`coins`·`messages`·`ready`·`held`(상한으로 보류된 수)·`baseline`(첫 실행 기준선 종목 수)·`failures`)를 14일간 보관한다. 실행 로그의 `OPPORTUNITY {...}` 줄에도 `hourlySent`·`dailySent`·`held`가 찍힌다.

**첫 실행 정책**(`RADAR_OPPORTUNITY_FIRST_RUN`) — preview(또는 꺼짐)에서 `on`으로 처음 전환할 때, 그리고 상태가 유실·손상돼 초기화된 뒤에도 적용된다:
| 값 | 동작 |
|---|---|
| `summary` (기본) | 현재 관찰 중인 모든 코인을 **알림 없이 기준선으로 기록**하고 *요약 1건*(LONG/SHORT 관찰 종목 이름·단계, 대기 수)만 보낸다. 이후 새 관찰·단계 상승·해제부터 알린다. 요약 전송이 실패하면 기준선을 확정하지 않고 다음에 처음부터 다시 한다 |
| `silent` | 요약도 보내지 않는다(기준선만 기록, 이후 이 코인들의 해제도 알린 적이 없으므로 조용히 처리) |
| `alert` | 기준선 없이 일반 규칙으로 알린다(우선순위·시간당·일일 상한은 그대로 적용되므로 한 번에 쏟아지지 않는다) |

미리보기(`preview`)는 첫 실행 때 어떻게 동작할지를 보여 준다(`NOTE`와 요약 메시지 본문). 분석된 종목이 하나도 없는 실행(전부 오래된 데이터 등)은 첫 실행으로 치지 않는다.

메시지는 3600자 안에서 나누고, 메시지마다 전송 확인 후에만 해당 코인의 "알림 완료" 상태를 저장한다. 전송 실패 시 상태를 확정하지 않아 다음 실행에서 다시 시도하며(누락 방지), 성공한 메시지는 다시 보내지 않는다(중복 방지). **상태 저장이 실패하면** 그 시점에서 더 보내지 않는다(저장되지 않은 채 전송이 늘면 재시작 때 중복이 늘어나므로). Telegram에는 멱등키가 없어 전송 직후 저장 전에 프로세스가 죽으면 드물게 한 번 중복될 수 있다(기존 레이더와 같은 한계). 429/403 등 제한 응답은 `Retry-After`·기존 정책(`waitMs`)만큼 쉰다.

## 3. 오탐 방지

- **확정봉만**: OKX `confirm=1` 캔들만 사용하고 진행 중인 봉은 버린다. 4H 봉은 신호 봉(1H)의 마감 시각까지 마감된 것만 쓴다.
- **정합성**: 시각 정렬·OHLC 범위·거래대금 단위·중복·누락 봉을 검사한다. 누락이 있으면 가장 최근의 연속 구간만 쓰고, 그래서 캔들이 모자라면 **대기가 아니라 '분석 제외'** 로 처리한다(알림·상태 변경 없음).
- **최신성**: 마지막 확정 봉이 직전에 마감한 봉이어야 한다. 방금 마감해 아직 확정 전이면 *확정 대기*(30분 유예, 5분 간격 재시도), 그 밖에 오래된 데이터면 분석 제외.
- **API 오류**: 목록 조회 실패는 알림 없이 백오프(10분 × 연속 실패 횟수, 최대 1시간). 403/418/429/451 제한 응답은 즉시 수집을 멈추고 기존 정책(`waitMs`)대로 대기한다. 개별 종목 실패는 그 종목만 제외한다. 기존 레이더가 제한 응답 대기 중이거나 상태 연속성 의심(`quiet`) 시간대면 같이 쉰다.
- **격리**: 어떤 예외·시간 초과(120초)도 기존 레이더 실행에 영향을 주지 않는다. 상태는 `state.opportunity` 아래에만 쓰며, 손상되면 안전하게 초기화한다.

## 4. 기능 플래그와 운영 분리

| 값 | 동작 |
|---|---|
| (미설정) / `off` / 그 밖의 모든 값 | **꺼짐** — 네트워크 호출·상태 변경 없음 (기본값) |
| `preview` | 분석과 메시지 생성만 하고 로그로 출력. 전송·알림 상태 저장 없음 |
| `on` | Telegram 전송 + 상태 저장 |

- 저장소 **변수**(`Settings → Secrets and variables → Actions → Variables`)로만 제어한다. 기존 `RADAR_SCHEDULER`와 무관하며 `radar.yml`의 `env`가 이 변수들을 그대로 넘긴다(미설정이면 아래 기본값).

| 변수 | 기본값 | 의미 |
|---|---|---|
| `RADAR_OPPORTUNITY` | `off` | `off` / `preview` / `on` |
| `RADAR_OPPORTUNITY_TOP` | `20` | 점검 종목 수 (1~30) |
| `RADAR_OPPORTUNITY_MIN_STAGE` | `2` | Telegram 알림 최소 단계 (1~3) |
| `RADAR_OPPORTUNITY_MAX_PER_HOUR` | `12` | 시간당 최대 알림 코인 수 (1~30) |
| `RADAR_OPPORTUNITY_MAX_PER_DAY` | `80` | 일일 최대 알림 코인 수 (1~200) |
| `RADAR_OPPORTUNITY_FIRST_RUN` | `summary` | `summary` / `silent` / `alert` |

범위를 벗어나거나 알 수 없는 값은 모두 기본값으로 되돌린다(`off` 포함).
- 이 변경이 기존 파일에 닿는 곳은 두 군데뿐이다: `radar-service/run.mjs`(정기 실행 *뒤에* 안전 래퍼 호출, 꺼져 있으면 즉시 반환) 와 `.github/workflows/radar.yml`(env 6줄 추가 — 스케줄·트리거·권한·단계는 그대로). 새 코드는 모두 `radar-service/opportunity/` 아래에 있다.
- 읽기 전용 점검: `node radar-service/opportunity/preview-cli.mjs --top 20` 또는 `opportunity-preview` 워크플로(Telegram 비밀값·상태 캐시 미사용).

운영 활성화 절차와 체크리스트는 **8절**.

## 6. 한계 (그대로 읽을 것)

- 연구에서 이 조건 구조(눌림목)는 **수익이 검증되지 않았다**. 알림은 "차트 조건이 갖춰졌다"는 사실이지 "오른다/내린다"는 예측이 아니다. 충족 점수는 조건 개수일 뿐이다.
- 4H 추세 조건이 엄격해 대부분의 코인은 *대기*다(실데이터 미리보기에서도 20종목 중 1~3종목 정도만 관찰 상태). 알림 빈도는 시장 상황에 크게 좌우된다.
- 1시간 단위 점검이므로 봉 중간의 움직임은 반영하지 않는다. 최대 지연은 봉 마감 후 5~10분(GitHub 스케줄 지연 포함).
- 유니버스는 24시간 거래대금 상위(OKX 암호화폐 USDT 무기한)이며 신규 상장(캔들 210개 미만)은 분석 제외다.
- 구간·무효화 가격은 규칙에서 기계적으로 계산한 값이다. 실제 거래의 손절·목표·수량을 대신하지 않는다.

## 8. 운영 활성화 전 체크리스트와 승인 절차

**현재 상태**: 코드는 Draft PR #27에만 있고 `main`에는 없다. 병합 전에는 어떤 운영 워크플로도 이 기능을 실행하지 않는다. 아래 모든 단계는 사용자의 승인이 있어야 진행한다 — 단계마다 사용자 확인을 받고 다음으로 넘어간다.

### A. 필요한 것 (이미 있는 것과 새로 만들 것)
| 항목 | 위치 | 상태 |
|---|---|---|
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | Settings → Secrets → Actions → **Secrets** | 기존 레이더가 쓰는 값 그대로 — **새 비밀값 없음** |
| `RADAR_OPPORTUNITY` | Settings → Secrets and variables → Actions → **Variables** | 새로 만들 변수(처음엔 `preview`) |
| `RADAR_OPPORTUNITY_TOP`, `_MIN_STAGE`, `_MAX_PER_HOUR`, `_MAX_PER_DAY`, `_FIRST_RUN` | 같은 Variables | **선택**. 만들지 않으면 기본값(20 / 2 / 12 / 80 / summary) |
| 기존 `RADAR_SCHEDULER` | 같은 Variables | **건드리지 않음** |

변수는 값이 비밀이 아니므로 UI에서 바로 확인할 수 있다. 토큰·chat ID는 문서·로그·PR에 쓰지 않는다.

### B. 단계별 절차
1. **검토·병합 승인** — PR #27 diff(기존 파일 변경은 `run.mjs`와 `radar.yml` env 6줄뿐)와 테스트 결과를 확인하고 병합을 승인한다. 이때 변수가 없으므로 기능은 여전히 꺼져 있다 → 병합 직후 첫 `radar` 실행 로그에 `OPPORTUNITY` 줄이 **없어야** 한다.
2. **preview 승인** — 변수 `RADAR_OPPORTUNITY=preview`를 만든다. 다음 `radar` 실행부터 로그에 `OPPORTUNITY {...}`, 코인별 상태, 보냈을 메시지가 나오고 **Telegram 전송과 알림 상태 저장은 없다**(최대 하루 정도 관찰). 확인할 것: 분석 종목 수·`excluded` 수, 관찰 종목 수가 과도하지 않은지, `calls`와 실행 시간, `held`/`dailySent`, 메시지가 읽을 만한지. 필요하면 이때 `MIN_STAGE`·`MAX_PER_HOUR`를 조정한다.
3. **on 승인** — `RADAR_OPPORTUNITY=on`으로 바꾼다. 첫 `on` 실행은 `FIRST_RUN=summary`이면 요약 1건만 보낸다("활성화 기준선"). 이후 새 관찰·단계 상승·해제만 알린다. **이 단계에서 처음으로 실제 Telegram 메시지가 나간다.**
4. **점검** — 첫 24시간 동안 하루 발송량(`state.opportunity.daily`, 로그의 `dailySent`/`held`), 같은 코인의 반복 알림 여부, 기존 정기 보고가 그대로인지 확인한다. 기준: 하루 알림이 일일 상한에 자주 닿거나 같은 코인이 해제 없이 반복되면 `off`로 되돌리고 원인을 본다.
5. **롤백** — 변수 `RADAR_OPPORTUNITY`를 삭제하거나 `off`로 바꾼다(다음 실행부터 즉시 꺼짐, 코드 되돌림 불필요). 기존 레이더·스케줄·Cloudflare에는 영향이 없다.

### C. 이 PR이 하지 않는 것
기존 정기 보고·스케줄·Telegram 설정 변경, Cloudflare 배포, `main` 병합, 운영 변수 변경, 실거래·주문·자동 진입·레버리지 기능. 실제 Telegram 전송은 한 번도 하지 않았고(테스트는 모두 모의 전송), 읽기 전용 미리보기 워크플로(`opportunity-preview`)만 공개 시세를 조회한다.
