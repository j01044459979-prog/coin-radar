# COIN RADAR 무료 5분 자동 실행 안정화

## 1. 문제 (실측)
main의 GitHub `schedule`(`*/5 * * * *`) 실제 시작 간격(2026-10-14 23:29 ~ 10-15 07:54 KST 기준 UTC, 18회·17개 간격):
**최소 15분 · 중앙값 28분 · 평균 약 30분 · 최대 44분** (목표 5분). GitHub 공식 문서도 고부하 시 schedule이 지연되거나 일부 큐가 버려질 수 있다고 안내하며 정확한 주기를 보장하지 않습니다.

## 2. 무료 실행 구조 비교
| 방식 | 무료 여부 | 5분 주기 | 판단 |
|---|---|---|---|
| GitHub `schedule` 단독 | 무료 | 실측 15~44분 지연 | 백업으로만 유지 |
| **Cloudflare Workers Cron Trigger → GitHub `workflow_dispatch`** | 무료 플랜 | 가능(분 단위 cron) | **선택** |
| Cloudflare Worker가 분석 전체를 직접 실행 | 무료 | — | 불가: 무료 CPU 10ms/호출, 서브요청 50개/호출 (분석은 OKX 약 220회 호출) |
| cron-job.org 등 외부 무료 cron | 무료 | 가능 | GitHub 토큰을 제3자 서비스에 맡겨야 해서 제외 |
| Google Apps Script 트리거 | 무료 | 1분 이상 | 토큰을 스크립트에 보관, 계정 종속 → 차선책 |
| Oracle 무료 VM 등 상시 서버 | 무료지만 | 가능 | "사용자 PC·서버 없음" 조건과 맞지 않아 제외 |

선택 이유: 이 저장소 계정에는 이미 Cloudflare Worker(`coin-radar-engine`)가 1분 cron으로 정상 동작 중이라 무료 Cron Trigger가 검증되어 있고, 분석·Telegram 전송·비밀값(Telegram)은 지금처럼 GitHub Actions 안에 그대로 두며, 디스패처는 "시작 신호"만 보냅니다.

Cloudflare 무료 플랜 한도(공식 문서): 요청 100,000/일, Cron Trigger 계정당 5개, 호출당 CPU 10ms(네트워크 대기 시간은 CPU에 불포함), 서브요청 50개/호출. 기존 Worker가 cron 2개를 쓰므로 디스패처 1개를 더해 3개. **한계**: Cloudflare cron도 시각 보증(SLA)은 없습니다. 실제 지연은 배포 후 로그로 확인해야 하며 이 PR에서는 미검증입니다(실배포 금지 조건).

## 3. 월 예상 무료 사용량
- Cloudflare: cron 288회/일 ≈ 8,640회/월(일 한도의 약 0.3%), 호출당 서브요청 2~3개(목록 조회 + dispatch), CPU는 1ms 미만 수준 예상. 기존 Worker(2,160회/일)와 합쳐도 일 한도의 약 2.5%.
- GitHub Actions: 실행 1회 약 2~3분 × 8,640 ≈ 월 21,600분(약 360시간). **공개 저장소의 표준 러너는 무료**입니다. 저장소를 비공개로 바꾸면 무료 한도(월 2,000분)를 넘으므로 비공개 전환 금지. 게이트에서 건너뛴 실행은 약 10~15초.
- GitHub API: dispatch 288회/일. 토큰 한도(시간당 5,000)에 비해 매우 적음.

## 4. 중복 실행 방지 (4겹)
1. **슬롯 번호**: 디스패처가 `slot = floor(예정시각/5분)`을 입력으로 보내고, 실행 이름에 `slot N`이 들어갑니다(`run-name`). dispatch 전에 최근 실행 목록에서 같은 슬롯이 있으면 건너뜁니다(cron 이중 발화·재시도).
2. **재시도 안전성**: dispatch 응답이 5xx/네트워크 오류여도 GitHub가 이미 접수했을 수 있으므로 재시도 전에 해당 슬롯 실행이 생겼는지 먼저 재조회합니다. 최대 3회, 짧은 Retry-After만 대기, 401/403/404/422는 재시도하지 않고 원인 힌트만 기록.
3. **대기 중 실행 확인**: 15분 이내에 대기(queued) 중인 실행이 이미 있으면 새로 보내지 않습니다(멈춘 대기 실행이 영구 차단하지 않도록 15분 초과분은 무시).
4. **워크플로 게이트**(`radar-service/gate.mjs`, 단위 테스트 포함): 캐시 복원 직후 **슬롯 번호(`state.lastSlot`)** 와 직전 시도 시각으로 판단 — 이미 처리한 슬롯과 그 이전 슬롯은 출처와 관계없이 다시 실행하지 않음(1차). 90초 간격은 슬롯 정보가 없는 호출을 위한 보조 규칙
   - Cloudflare 디스패치: `RADAR_SCHEDULER=cloudflare`일 때만 실행, 이미 처리한 슬롯이면 건너뜀(보조: 직전 시도 90초 이내). **`github`(롤백) 상태면 무시**.
   - GitHub schedule: 변수가 `cloudflare`면 평소엔 대기, **마지막 시도가 15분 넘게 없으면 대신 실행**(Cloudflare 장애 자동 복구).
   - 수동 실행·푸시: 항상 허용.
   - `concurrency: radar` + `cancel-in-progress: false`는 그대로(동시 실행 금지). 단, "대기 1개가 새 대기로 교체되는지" 같은 GitHub 내부 동작은 공식 문서로 확인하지 못해 **의존하지 않도록** 위 1~4번으로 설계했습니다.
5. Telegram 중복: 기존 정기 보고(시간대 1회)·긴급 알림 쿨다운·`state.partial` 재개 로직이 그대로 적용되고, 수집 자체가 슬롯당 1회로 제한되어 중복 가능성이 더 낮아집니다.

## 5. 캐시(상태) 안정성
- 복원: `key: radar-state-${run_id}`는 항상 미스 → `restore-keys: radar-state-` 접두어 중 **가장 최근에 만들어진 캐시**가 복원됩니다. `concurrency`로 실행이 직렬화되어 "최신 = 직전 실행"이 보장됩니다. 캐시는 브랜치별로 격리되어(feature 브랜치 프리뷰 캐시는 main이 읽지 않음) main의 schedule/dispatch 실행끼리만 상태를 이어받습니다. 7일 미사용·저장소 10GB 초과 시 오래된 것부터 삭제되나 5분마다 갱신되어 해당 없음.
- 수동 실행/재시도(re-run): 같은 run_id의 attempt 2는 `...-2` 키로 저장되어 충돌하지 않고 항상 최신이 복원됩니다.
- 저장 실패 대응(신규): 저장 검증이 실패하면 `-retry` 키로 다시 저장·검증하고, 그것도 실패해야 실행이 빨갛게 표시됩니다(상태가 오래된 값으로 되돌아가 보고가 중복되는 위험 감소).
- 손상 대응(신규): 상태 JSON이 깨져 있으면 이전에는 실행이 계속 실패했습니다(가장 최근 캐시가 계속 복원되므로 영구 정지). 이제 원본을 `state.corrupt-<시각>.json`으로 보존하고 새 상태로 시작하며 `::warning::`을 남깁니다(정기 보고 1회 중복 가능).
- 추적(신규): 저장마다 `seq`, `savedAt`을 기록하고 게이트 로그에 복원된 값을 출력해 어떤 캐시가 복원됐는지 확인할 수 있습니다.
- 대안 비교: ① Cloudflare KV(무료 쓰기 1,000회/일 — 288회면 가능하나 Actions에서 Cloudflare 토큰이 추가로 필요) ② 별도 `radar-state` 브랜치에 커밋(영구적이지만 5분마다 커밋 1년 10만 건, 노이즈) ③ Gist. 현재 방식(캐시+검증+재저장)이 추가 비밀값·권한 없이 충분하다고 판단해 유지하고, 캐시 유실이 실제로 반복되면 KV로 전환하는 것을 권합니다.

## 6. 전환 절차 (사용자 승인 후, 한 단계씩)
0. PR 병합(승인). 워크플로가 main에 있어야 dispatch 입력(`source`, `slot`)이 인식됩니다. 병합 직후에는 변수가 없으므로 기존 GitHub schedule 방식 그대로입니다.
1. GitHub 토큰 만들기 — https://github.com/settings/personal-access-tokens/new : Repository access = *Only select repositories* → coin-radar 하나, Permissions → **Actions: Read and write**(Metadata: Read-only 자동), 만료 90일~1년. 생성된 토큰은 채팅에 붙여넣지 않습니다.
2. Cloudflare 대시보드 → Workers & Pages → Create → 이름 `coin-radar-dispatcher` → `scheduler/worker.mjs` 내용을 붙여넣어 배포.
3. Settings → Variables and Secrets: Secret `GITHUB_DISPATCH_TOKEN`(1단계 토큰), Variable `DISPATCH_ENABLED=false`(아직 꺼 둠). Settings → Triggers → Cron `*/5 * * * *` 추가. (`scheduler/wrangler.toml`에 같은 값이 있음.)
4. 확인: 몇 분 뒤 Worker 로그에 `"decision":"disabled"`가 5분마다 찍히면 cron이 정상. 이때 GitHub는 호출하지 않습니다.
5. 전환: GitHub → Settings → Secrets and variables → Actions → Variables → `RADAR_SCHEDULER` = `cloudflare` 추가 → 이어서 Worker의 `DISPATCH_ENABLED`를 `true`로. (순서가 바뀌어도 게이트가 중복을 막습니다.)
6. 확인(15~20분): Actions 목록에 `radar · workflow_dispatch · cloudflare · slot N`이 5분 간격으로 나타나고, GitHub schedule 실행은 "건너뜀" 로그(`GATE 건너뜀`)와 함께 짧게 끝나야 합니다.
7. **롤백**: `RADAR_SCHEDULER` 변수를 `github`로 바꾸거나 삭제(즉시 적용 — 디스패치는 게이트에서 무시) + Worker `DISPATCH_ENABLED=false`. 코드 변경·재배포 불필요.
8. 유지: 토큰 만료 전에 재발급해 Secret만 교체. 만료/권한 오류는 Worker 로그에 `rejected`(401/403)로 남고, 그동안 GitHub schedule이 15분 공백 후 자동으로 대신 실행됩니다.

## 7. 미검증 사항(정직한 한계)
- 실제 Cloudflare cron 지연과 dispatch 후 러너 시작 지연은 배포 후 측정 필요(이 PR에서는 배포·실행 금지).
- GitHub 대기열 교체/60일 무활동 시 schedule 자동 비활성화 등 일부 동작은 공식 문서를 이 환경에서 직접 확인하지 못했습니다(문서 사이트 접근 불가). 설계는 이에 의존하지 않습니다.
- 5분 정확성은 보장되지 않으며 목표는 "대부분 5~7분 이내".

## 8. 2차 검토 보완 (PR #21 리뷰 반영)
### 8-1. 디스패처 중복 방지의 한계와 최종 보장 (검토 1)
- 디스패처의 "실행 목록 확인"은 **최선의 확인**입니다. GitHub 실행 목록은 dispatch 직후 몇 초 늦게 반영될 수 있고, 목록 길이 제한이 있으며, Worker는 호출 사이에 기억을 갖지 않습니다. 그래서 조회 범위를 최근 30분·최대 50개로 좁히고(`created` 필터), 재시도 전 재조회를 유지하되, 목록에 안 보이면 같은 슬롯이 두 번 dispatch될 수 있음을 인정합니다(테스트로 재현).
- **최종 멱등성은 워크플로 Gate가 보장**합니다: 같은 슬롯이 몇 번 도착해도 수집·분석·Telegram 전송은 한 번만 일어납니다(테스트: 슬롯 3건 도착 → 실행 1건).
### 8-2. 90초 게이트만으로는 부족했음 (검토 2)
- 재현: 같은 슬롯의 두 번째 요청이 첫 실행(약 2분)이 끝난 뒤 시작하면 직전 시도가 90초보다 오래되어 **중복 분석이 실행됩니다**(이전 게이트 시뮬레이션 테스트). Telegram은 시간대 1회·쿨다운 로직이 있어 대부분 막히지만 분석·상태 갱신은 중복입니다.
- 보강: 디스패처가 보낸 `slot`(없으면 현재 시각 기준 슬롯)을 Gate가 `state.lastSlot`과 비교해 같거나 오래된 슬롯을 건너뜁니다. 실행 시작 시 `lastSlot`을 먼저 기록·저장합니다. 늦게 도착한 이전 슬롯 요청, 뒤바뀐 순서도 무시됩니다. 연속 슬롯 12개는 모두 실행됩니다(과잉 억제 없음). 한계: 실행이 저장 전에 비정상 종료되면 그 슬롯이 처리된 것으로 기록되지 않아 다시 실행될 수 있습니다(5분 뒤 다음 슬롯이 어차피 실행).
### 8-3. 오래된 캐시 복원과 Telegram 중복 (검토 3)
- 위험: 복원이 최신 캐시를 놓치면 `reportHour`·강한 신호 쿨다운이 과거 값이 되어 **같은 시간대 정기 보고가 다시 전송될 수 있습니다**(억제 없는 상태에서 재현됨).
- 최신 상태 확인: 복원 직후 `Check cache freshness`가 GitHub 캐시 목록(`actions: read`, 읽기 전용)에서 가장 최근 `radar-state-*` 캐시를 찾아 복원된 키와 비교합니다. 더 새 캐시가 있으면 그 키로 **정확히 재복원**(`Restore newest cache`)합니다. 복원 기준은 계속 접두어 복원(가장 최근)이며 목록은 검증용입니다(목록 지연이 더 오래된 키로 되돌리지 않도록).
- 안전한 억제: 재복원도 실패하거나(`stale`) 캐시가 있는데 복원이 안 된 경우(`cold-with-caches`)에는 이번 시간대 Telegram 전송을 **억제(quiet)** 합니다 — 정기 보고·긴급 알림을 보내지 않고, 보고 시각과 강한 신호 쿨다운만 기록하며, 다음 시간대부터 정상 재개합니다(1회 생략 > 중복 전송). 수집 장애 알림은 억제하지 않습니다. 최초 실행(캐시가 전혀 없음)과 확인 API 실패(`unverified`)는 억제하지 않습니다(알림 자체가 막히는 것을 피하기 위함).
- 한계: 캐시 목록과 복원이 모두 오래된 값을 보이는 경우는 탐지할 수 없습니다. 이 경우의 최대 영향은 정기 보고 1회 중복입니다. 근본적 해소가 필요하면 Cloudflare KV 등 외부 저장소가 필요합니다(추가 비밀값·권한 필요 → 사용자 승인 사항).
### 8-4. 15분 자동 복구와 정상 Cloudflare의 충돌 여부 (검토 4)
- 시뮬레이션(지터 0~100초, 실행 2분, GitHub schedule 15~45분 간격, 시드 5개 × 60슬롯): **Cloudflare 정상 시 GitHub schedule 실행 0회, 슬롯 중복 0회**. Cloudflare가 20분 멈추면 15분 초과 시점부터 GitHub schedule이 대신 실행하고, 복귀 후에도 같은 슬롯 중복은 없습니다. 롤백 상태에서는 남은 디스패치가 모두 무시됩니다.
- 한계: 수집 제한(403/451)으로 1시간 대기 중일 때는 `lastAttempt`가 갱신되지 않아 15분 후 GitHub schedule도 깨어나지만, 수집 대기(`retryAt`)가 그대로 적용되어 수집·전송은 없습니다(빈 실행만 발생).
### 8-5. 손상된 캐시 복구 정책 (검토 5)
- 이전: 새 상태로 시작 → 같은 시간대 정기 보고 1회 중복 가능. **변경**: 손상 복구도 위 억제(quiet) 정책을 적용합니다 — 원본은 `state.corrupt-<시각>.json`으로 보존, 새 상태로 시작하되 이번 시간대 전송은 하지 않고 `::warning::`만 남깁니다. 사용자 알림을 자동으로 보내지 않으므로 Actions 로그/경고에서 확인해야 합니다.

## 9. 최종 안전성 검토 (e458dcc 기준)
### 9-1. `actions/cache/restore@v4` 출력 의미 (공식 README/action.yml 확인)
- `cache-hit`: **기본 키(`key`)가 정확히 일치할 때만 `true`**. `restore-keys` 접두어 부분 일치나 미스는 `false`(미스에서 빈 값일 수도 있어 `== 'true'`만 성공으로 취급).
- `cache-matched-key`: 복원된 캐시의 키(정확 일치면 기본 키, 아니면 일치한 restore-keys 항목의 캐시 키). 복원이 없으면 비어 있음.
- 따라서 1차 복원(`key: radar-state-<run_id>` + 접두어 restore-keys)은 항상 부분 일치라 `cache-hit`이 `false`이며, **`cache-matched-key`로 판단**한다(워크플로 테스트로 `steps.restore.outputs.cache-hit` 미사용을 강제). 최신 캐시 재복원 단계는 `restore-keys` 없이 정확한 키만 쓰므로 `cache-hit == 'true'`가 곧 "그 캐시를 그대로 복원함"이다. 복원 오류는 단계 실패가 아니라 경고이므로 출력이 비게 되고, 이 경우 stale/억제 경로로 처리된다.
- 한계: 위 의미는 공식 문서/action.yml 기준이며 이 환경에서 실제 Actions 실행은 금지되어 실측하지 못했다. 병합 후 첫 실행 로그의 `CACHE 복원 키=… · 최신 키=… · 판정=…` 줄로 확인한다.
### 9-2. 캐시 API 실패(`unverified`)와 재복원 실패 시 중복 전송 가능성
| 상황 | 판정 | 결과 |
|---|---|---|
| 목록 조회 성공, 복원 키가 최신 | ok | 정상 |
| 더 새 캐시 존재 → 정확한 키로 재복원 성공 | ok | 정상(최신 상태) |
| 더 새 캐시 존재 → 재복원 실패 | stale | **그 시간대 전송 억제**(중복 0) |
| 캐시가 있는데 1차 복원 실패 → 재복원 실패 | cold-with-caches | 전송 억제 |
| 복원 키가 목록에 없음(목록 반영 지연) | unverified | stale로 단정하지 않음(오래된 캐시로 되돌려 복원 방지) |
| API 오류 3회 재시도 후에도 실패 | unverified | 상태가 **직전 슬롯과 정확히 이어질 때만** 진행, 아니면 억제 |
- 이전(e458dcc)에는 `unverified`면 무조건 진행했고, 그 경우 한 실행 뒤처진 상태가 복원되면 정기 보고가 다시 나갈 수 있었다. 이제 `unverified`에서도 `state.lastSlot == 현재 슬롯 − 1`이 아니면(상태 없음 포함) 그 시간대 정기 보고·긴급 알림을 억제한다. 한 실행이라도 뒤처진 상태는 `lastSlot`이 한 칸 이상 벌어지므로 걸러진다. 비용: 정당한 슬롯 누락(Cloudflare cron 누락)과 API 장애가 겹치면 그 시간대 보고 1회가 생략된다(다음 시간대 정상).
- 캐시 확인 API는 5xx·네트워크·429(Retry-After, 최대 10초)에서 최대 3회 재시도하고, 401/404 같은 설정 오류는 재시도하지 않으며, 토큰은 Authorization 헤더로만 쓰고 출력하지 않는다.
### 9-3. 남은 위험 (정직한 목록)
1. **전송 후 캐시 저장이 두 번 모두 실패**하면(저장 + `-retry` 저장) 다음 실행은 직전 전송을 알 수 없다. 캐시 목록상 "최신"은 오래된 캐시이므로 `ok`로 판정되어 정기 보고가 1회 중복될 수 있다. 실행이 빨갛게 표시되므로 인지는 가능하지만 자동 차단은 못 한다. 해소하려면 전송 기록을 캐시 외부(Cloudflare KV 등)에 두어야 한다 → 추가 비밀값·승인 필요.
2. 캐시 목록 API와 복원이 **동시에** 같은 오래된 값을 보이면 탐지할 수 없다(최대 영향: 정기 보고 1회 중복).
3. 위 `unverified` 억제는 GitHub schedule 모드(기본, 슬롯이 시각 기반이라 연속성이 거의 성립하지 않음)에서 API 장애 시 그 시간대 보고를 생략한다. 장애 자체가 드물어 허용.
4. 실제 Actions·Cloudflare 실행 없이 검증했다: 캐시 목록 필드(`key`, `created_at`)와 `cache-matched-key` 값 형식은 문서 기준이며 첫 실행 로그로 확인해야 한다.
5. Cloudflare cron 지연, dispatch 후 러너 시작 지연은 여전히 배포 후 측정 필요.
