# R4 — Telegram 처리 (오프라인 개발 완료, 운영 연결 없음)

상태: 코드·테스트 완료. **실제 Telegram 호출·운영 배포·병합은 하지 않았습니다.** 모든 테스트는 가짜 Telegram 서버(`test/helpers/faketg.mjs`)로 실행하며, 실제 봇 토큰은 필요 없습니다.

## 구성
| 파일 | 역할 |
|---|---|
| `lib/tg.mjs` | 수신 처리 엔진(순수 로직, 네트워크·시트·키 저장소는 env 포트 주입) |
| `gas/Telegram.gs` | Apps Script 어댑터: 토큰·kv(Script Properties)·UrlFetch·1분 폴링 트리거·페어링 코드·입력 화면 라우팅 |
| `gas/Fill.html` | 모바일 입력 화면(진입/청산, 숫자 키패드, 다크/라이트, 외부 스크립트 없음) |
| `gas/Api.gs`(R5 브랜치) | `doGet` 라우터(`?p=fill`)와 소유자 이메일 확인(fail-closed) |

## 사용자 흐름
1. 신호 알림: `🔔 A전략 LONG BTCUSDT / 진입·손절·TP1 / 내 판단은?` + [진입했어][관망했어][놓쳤어]
   (`callback_data = r1:{sid}:{e|w|m}`, 64바이트 이내. sid는 영문·숫자·`_.-` 54자 이하)
2. 버튼 1회 = 응답 1건(sid 유일키). 재클릭·재전달은 부수효과 없음, 다른 선택은 기존 기록을 바꾸지 않음("수정은 앱에서"). 처리 후 키보드 제거.
3. **진입했어** → `/fill 신호ID 증거금 레버리지 진입가 손절가 [qty= fee= funding=]` 안내(+ 입력 화면 버튼). 수량을 생략하면 증거금×레버리지÷진입가로 계산(표시에 "(계산)").
   요약(손절 시 손실, 경고)과 [저장][취소] 확인 후에만 기록. 저장하면 "진입했어" 응답도 함께 기록.
4. 청산: `/exit 신호ID 청산가 [수량|all] [fee= funding=]`. 잔량보다 적으면 부분청산(reduce), 같으면 전량(close). 수량 초과·진입 없음·이미 청산은 안내만 하고 초안도 만들지 않음.
   추가 진입은 같은 신호에 `/fill`을 다시 쓰면 `add`.
5. 수수료·펀딩: `fee=0.12` 입력, `fee=~0.12` 추정, 생략하면 미입력(R2의 3상태). 미입력은 합계에서 제외되고 표시됨.
6. 10초 복기: 전량 청산 저장 직후 `복기` 메시지(계획 4택·심리 4택·저장 버튼). **기본값(계획대로·침착)은 표시만** 하며 저장 버튼을 눌러야 기록. 선택 변경은 화면만 바뀜(선택 상태는 callback_data에 담아 서버 상태 없음). 같은 내용 재저장은 unchanged, 수정은 리비전. `/review 신호ID`로 다시 열 수 있음.
7. `/status`: 열린 포지션 목록. `/help`.

## 모바일 입력 화면과 `/fill` 연계
- 입력 화면(`?p=fill`)은 소유자 이메일 확인 후에만 열리고, 신호 알림 버튼의 링크가 `sid·방향·진입가·손절가`를 미리 채웁니다(값은 서버가 JSON으로 주입, `<` 이스케이프).
- 폼 제출이 곧 확인입니다. 화면이 열릴 때 만든 `formId`로 fillId를 고정하므로 더블탭·네트워크 재시도는 `duplicate`로 수렴합니다(상태가 바뀐 뒤 재제출해도 동일).
- `/fill`·화면·`/exit`은 같은 빌더(`tgBuildEntry`/`tgBuildExit`)와 같은 저장 경로를 씁니다.

## 인증·보안
- **페어링**: UI(소유자 로그인)가 10분·1회용 코드(해시만 저장)를 만들고, 봇에 `/pair 코드`를 보낸 계정의 `from.id`만 저장(하드코딩 없음). 5회 실패 시 코드 폐기, 그룹·봇 계정 불가, 실패는 무응답.
- 페어링 외 발신자(그룹 포함)는 **무응답·무기록**. 코드/Telegram ID/토큰은 로그에 남기지 않음.
- 토큰은 `Telegram.gs` 의 `http.call` 안에서만 읽습니다. 엔진은 토큰을 볼 수 없고, 네트워크 오류 메시지(URL 포함 가능)는 버려 상태 코드만 반환합니다(테스트로 확인).
- **자동 주문 없음**: 이 모듈은 기록만 합니다(소스에 주문 호출 없음을 테스트로 고정).

## 오류·재시도
| 상황 | 처리 |
|---|---|
| 429 | `retry_after` ≤ 10초면 대기 후 재시도(최대 3회). 더 길면 다음 트리거로 넘김 |
| 5xx·네트워크 | 0.5초, 1초 후 재시도(최대 3회), 이후 `retryable` 반환 |
| 400/401/403/404/409 | 재시도 없음, 분류 코드만 반환(`forbidden`·`auth`·`conflict`…). 만료된 버튼·사라진 메시지·수정 불필요는 무해 처리 |
| 저장 후 응답 전송 실패 | 기록을 되돌리지 않고 `replyFailed`로 집계 |
| 저장은 됐는데 update 기록(claim) 실패 | 오프셋을 올리지 않고 다음 틱에 재처리 → sid·fillId 유일키로 같은 결과(중복 없음) |
| 같은 update가 3번 연속 실패 | 건너뜀(폴링이 막히지 않음), `poison` 집계 |
| 동시 폴링 | 55초 리스(kv)로 방지 |

## 중복 방지
`update_id`(`u:`)·`callback_query.id`(`cb:`)를 처리 성공 후 기록, 처리 전에 이미 있으면 무시. 그 이전 재전달은 응답(sid)·체결(fillId)·복기(sid) 유일키로 수렴. 오프셋은 kv에 영속(유실돼도 중복 기록 없음).
