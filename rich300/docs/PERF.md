# RICH 300 웹앱 속도·무한 로딩 대응

## 1) 무한 로딩(빈 화면) — 코드에서 찾은 원인과 조치
| 원인(코드 근거) | 증상 | 조치 |
|---|---|---|
| `doGet` 이 소유자가 아니거나 `p` 가 없으면 **빈 응답**을 돌려줌 | 모바일(특히 텔레그램 등 앱 내 브라우저는 로그인 정보가 전달되지 않음)에서 하얀 화면·로딩이 끝나지 않는 것처럼 보임 | 소유자가 아니면 **접근 안내 화면**(데이터 없음), 소유자가 주소만 열면 **메인(dash)**. 어떤 경우에도 화면을 돌려줌 |
| 한 번 열 때 Sheets 호출 130~260회·읽은 셀 10만~32만 개(90일 이력). 기록이 쌓일수록 느려져 Apps Script 실행 시간 안에 못 끝날 수 있음 | 화면이 오래 안 열림 | 아래 2) 성능 개선 |
| 페이지 함수가 던진 예외는 화면에 안내만 있고 **다시 시도 버튼·원인 코드 없음** | 막다른 화면 | 모든 오류 화면에 **오류 코드 + 다시 시도 + 상태 점검** 링크 |
| 배포가 *예전 버전*에 고정(clasp push 는 HEAD 만 바꿈, `/exec` 는 배포된 버전 실행) | 새 코드를 올려도 예전 화면·오류 그대로 | `?p=health` 에 **코드 빌드 ID** 표시 → 올린 빌드와 비교. 아래 3) 새 버전 배포 |
| `Fill.html` 서버 호출에 응답이 없으면 버튼이 계속 비활성 | 저장 버튼이 영원히 '저장 중' | 20초 무응답 시 풀리고 같은 내용(같은 formId)으로 안전하게 재전송 |
| (부수) 일지 화면 `<head>` 태그가 `<jvHead>` 로 잘못 들어가 있었음 | viewport 메타가 본문에 위치 | 수정 |

**상태 점검 화면 `?p=health`**(소유자 전용, 읽기 전용): 코드 빌드 → 스크립트 속성 → 스프레드시트 열기 → 시트 구조 → 챌린지 → 최근 기록 → 트리거 → 웹앱 주소 → **첫 화면·기록 조회 실제 생성 시간** → 최근 응답시간(첫 실행/재실행 구분). 각 단계가 독립이라 한 곳이 실패해도 화면은 열리고 FAIL 항목에 짧은 코드만 나옵니다(시트 값·ID·이메일 없음).

## 2) 성능 개선 (동작·기록 정확성 불변)
- **요청 단위 읽기 캐시**(Adapters.gs): 같은 시트를 한 요청에서 여러 번 읽어도 Sheets 호출 1번. *다음 요청으로 넘어가지 않으므로* 잔고·포지션·체결이 오래된 값이 되지 않음. 락을 잡은 직후 Audit 마지막 행이 바뀌었으면 캐시를 전부 버림(락 대기 중 다른 실행이 쓴 행 반영).
- **끝부분만 읽기**: 쓰기 경로가 감사 로그·엔티티 시트를 전체 읽던 것을 마지막 몇 행만 읽음(해시 체인·복구 의미 동일).
- **초기화 확인 표시**: 14개 시트 머리글을 매 요청 재확인하던 것을 1시간 캐시(스키마 버전 키). `?p=health` 는 항상 전체 재확인.
- **쓰기 한 번에**: 응답·체결·분할매매 계획(PR #43) 저장을 **락 한 번**(재진입)으로, `flush` 는 락 해제 직전 1회. 중복 판정도 락 안에서 하므로 동시 요청이 서로의 직전 기록을 봄.
- **기록 조회**: 최근 40건부터, `더 보기`로 40건씩(최대 200). 수정 이력(Audit)은 수정된 항목이 화면에 있을 때만 읽음. 통계·자산 탭은 목록을 만들지 않음.
- **저장 화면**: 즉시 '저장 중… N초', 연타 차단, 무응답 20초 뒤 재시도 안내(같은 formId → 중복 저장 없음).
- 캐시하지 않는 것: 잔고·평가액·포지션·체결·계획 값(요청 간 캐시 없음). 대시보드 결과물 자체도 캐시하지 않음.

## 3) 운영 URL·Deployment ID 를 유지한 채 새 코드 반영
1. 코드 반영: `clasp-install.sh`(PR #44) 로 push — 새 프로젝트를 만들지 않습니다.
2. **새 버전으로 기존 배포 갱신**(주소·Deployment ID 불변): Apps Script 편집기 → 배포 → **배포 관리** → 기존 '웹 앱' 배포의 ✏️(편집) → 버전 **새 버전** → 배포. (새 배포 만들기를 누르면 주소가 바뀌니 누르지 않습니다.)
   - CLI 대안(Cloud Shell, 기본 권한으로 로그인한 clasp 3.x): `clasp redeploy <DEPLOYMENT_ID> -d "perf"` — 설치 스크립트의 최소 권한 로그인에는 `script.deployments` 가 없어 별도 로그인이 필요합니다.
3. 확인: `<웹앱 주소>?p=health` 의 **코드 빌드**가 설치 스크립트가 출력한 빌드와 같고, 모든 항목이 PASS 인지 봅니다. 같지 않으면 2단계가 안 된 것입니다.
4. 기본 `appsscript.json`(실행: 접속한 사용자 / 접근: 나만)은 그대로입니다. 실거래 자동 주문은 없습니다.

## 4) 남은 병목(정직한 한계)
- **실제 Google 지연은 측정하지 못했습니다**(이 환경에서 Google 접근 불가). 배포 후 `?p=health` 의 실측(H9·H10)과 '최근 응답시간'이 진짜 기준입니다.
- 진입 저장은 쓰기 6회(Audit+엔티티 ×3: 응답·체결·계획)와 `setNumberFormat` 6회, flush 1회가 남아 모델상 2.3초. 한 번에 여러 행을 쓰는 배치 쓰기(Audit 3행 → 1회)는 선기록 순서 보장 때문에 이번에는 하지 않았습니다.
- 체결(Fills) 시트는 한 번 전체를 읽습니다(키 조회). 체결이 수천 건이 되면 읽는 셀이 선형 증가 → 그때는 월별 시트 분리 또는 TextFinder 조회가 필요합니다.
- 초기 실행(캐시 비어 있음)의 첫 화면은 시트 머리글 확인 때문에 호출이 더 많습니다(1시간에 한 번).
- 청산 저장은 페어링된 경우 Telegram 복기 안내 전송(UrlFetch ~0.5초 가정)이 응답 시간에 포함됩니다.
- Apps Script 콜드 스타트(수 초)는 코드로 줄일 수 없습니다. 첫 실행이 느리면 '10분마다 가벼운 트리거로 깨우기'를 검토할 수 있으나 이번 범위에는 넣지 않았습니다.
