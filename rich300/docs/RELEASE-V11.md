## 실행 순서 (사용자 직접 작업은 ★ 표시, 총 3가지)
1. **main 반영**(내가 수행, 승인 후): 최소 브랜치 PR 생성·병합. 병합되어도 `RADAR_RICH300_FEED` 가 없으므로 radar 동작은 그대로(artifact 단계는 조건 불충족으로 건너뜀).
2. ★ **GitHub 설정 2건**(Settings → Secrets and variables → Actions): ① Secret `RICH300_FEED_KEY` = 임의의 40자 이상 문자열(예: `openssl rand -base64 36 | tr -d '/+='`) ② 변수 `RADAR_RICH300_FEED` = `on`. *Secret 을 먼저, 변수를 나중에* 설정한다(변수가 켜지는 순간부터 피드가 만들어진다).
3. **피드 게시 확인**(내가 수행): 다음 정기 radar(main, 5분 주기) 성공 뒤 `rich300-feed` 워크플로가 성공하고 `rich300-feed` 브랜치에 `feed.json` 이 생겼는지 확인(없으면 원인 보고, 이후 단계 중단).
4. **v11 배포**(내가 수행, 승인 후): 기존 Deployment ID·URL 유지. 백업 → 반영 → 새 버전 → 배포 갱신 → API 로 버전·빌드·해시 검증. **전략 추적은 꺼진 채** 배포(속성·트리거 불변).
5. ★ **`?p=ops` 4번 구역**(편집기·GitHub 불필요): 2번의 같은 키 붙여넣기 → 사전 점검(Telegram·피드 서명·시세·미리보기) → `전략 추적 시작`. 사전 점검을 통과해야만 시작되고 실패하면 자동 복구.
6. ★ 이후 관찰: `?p=strat` 에서 신규 전략·진행을 본다. 문제가 있으면 `전략 추적 중지` 한 번.

## 롤백 (빠른 순서)
1. 전략만 멈춤: `?p=ops` → `전략 추적 중지`(RICH300_STRATEGY=off. 실전 위치 감시가 켜져 있으면 트리거 유지).
2. radar 피드 중단: GitHub 변수 `RADAR_RICH300_FEED` 를 `off`(또는 삭제) → radar 는 즉시 기존 동작, 피드 워크플로는 실행되지 않음.
3. Apps Script 되돌리기(내가 수행): 기존 배포를 **v10** 으로 되돌림(`deployments.update`, Deployment ID·URL 불변). v10 코드는 전략 속성을 읽지 않는다. `Strategies` 시트와 `w:sg:*` 속성은 남지만 무해(삭제하지 않음).
4. main 되돌리기(필요할 때만): 최소 브랜치 병합 커밋 revert.
항상 이 순서(1→2→3→4)로, 위험이 큰 쪽(전송)부터 끈다.
