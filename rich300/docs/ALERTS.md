# RICH300 보유 포지션 관리 알림

범위: 웹앱에 *사용자가 실제 체결로 등록한 포지션*만 감시한다. 추천 후보·미체결 감시 후보는 대상이 아니다. **Binance 주문·계정 API 없음(자동 주문 없음).**
상태: **구현됨(`lib/watch.mjs`, `gas/Watch.gs`) · 기본 OFF · 감시 트리거 미설치 · Telegram 실전 알림 미활성** (활성화는 사용자 승인 후).

## 1) COIN RADAR 추천 알림과의 구분
| 구분 | COIN RADAR 추천(GitHub Actions) | RICH300 보유 포지션 감시(Apps Script) |
|---|---|---|
| 대상 | 시장 전체의 진입 후보·기회 감시 | 사용자가 체결로 등록한 보유 포지션만 |
| 실행 | `radar.yml` (cron */5, 실제 간격은 GitHub 지연) | 시간 트리거 `rich300WatchTick` 5분 (설치 전 없음) |
| 상태 저장 | Actions 캐시 `.radar-state` | Script Properties `w:` 접두 (`tg:` 입력 상태와도 분리) |
| 켜는 곳 | 저장소 변수 `RADAR_SIGNAL`, `RADAR_OPPORTUNITY` | 스크립트 속성 `RICH300_WATCH_ALERTS` = `off`(기본) / `preview` / `on` |
| 전송 가드 | 시크릿 존재 | 기존 `rich300TgGate_`(운영 승인) + Telegram 연결(페어링). 하나라도 없으면 `on` 이어도 미리보기만 |

## 2) 입력 구분
- **내 체결**: 웹앱/텔레그램에 등록한 Fills(평균 진입가·남은 수량·방향·입력한 손절가). 시세로 덮어쓰지 않는다.
- **시세**: 거래소 공개 API, 읽기 전용. 출처는 OKX(우선) → Bybit(대체). 메시지에 `시세(OKX HH:MM, N분 전)` 로 표시한다. Binance 체결가와 다를 수 있음을 명시한다. 키·계정 연동 없음.
- 시세가 10분 넘게 오래됐거나 봉이 부족하면 판단을 만들지 않는다. 모든 종목이 연속 3회 실패하면 "시세 수집 장애"를 한 번만 알린다.
- 종목을 알 수 없는 포지션(신호 없음)은 감시하지 않고 건너뛴다 — 임의 종목 수동 등록은 3단계(웹앱 단순화)에서 종목 입력과 함께 추가한다.

## 3) 알림 종류와 규칙 (모두 수치 조건 · `lib/watch.mjs` 의 `WATCH`)
R = 분할 계획의 R(진입−손절 거리), 계획이 없으면 |평균 진입가−입력 손절가|. 봉은 *마감된 봉만* 쓴다. 추세: 종가>EMA50, EMA20>EMA50, EMA50 상승(롱) / 반대(숏). 거래량 비율: 마지막 마감 봉 ÷ 직전 20봉 평균.
| 알림 | 조건 | 사용자가 직접 할 행동 |
|---|---|---|
| 손절가 이탈 `STOP_BREACH` | 시세가 현재 손절 기준을 넘음 | 거래소에서 체결 여부 확인, 체결됐으면 웹앱에 청산 등록 |
| 손절 임박 `STOP_NEAR` | 손절까지 ≤0.25R. 0.5R 밖으로 벗어났다가 재접근하면 새 알림 | 손절 주문 확인, 손절을 넓히지 않기 |
| 손절 위험 `STOP_TREND` | 손절까지 ≤0.6R + 1h 추세 반대 + 1h 거래량 ≥1.2배 (쿨다운 60분) | 손절 유지 점검, 추가 진입 금지 |
| TP1·TP2 `TP1/TP2` | +1.5R / +2R 가격 도달(분할 계획 가격). 이미 청산 등록된 구간 제외 | 50% / 30% 부분 청산 후 등록 |
| 추가 진입 조건 충족 `ADD_READY` | 사전 지정 N차 가격(허용오차 0.15R) 도달 + 손절 안쪽 + 1h 추세 유지 + 1h 거래량 ≥1.0배 + 계획 검사(`splanCheckAdd`: 총 최악 손실이 위험 예산 이내) + 일일 손실 한도 미도달 | N차 수량을 지정가로 직접 주문, 체결 후 등록 |
| 추가 진입 취소 `ADD_CANCEL` | 익절 시작 · 구조 이탈(직전 15분 종가) · 허용 시간 경과 · 4h 추세 반전 | 미체결 추가 주문 취소 |
| 추적손절 `TRAIL` | TP1 뒤 본전, TP2 뒤 고점−1R 추적. **유리한 방향으로만**, 0.25R 이상 이동 시 | 거래소 손절을 지정 가격으로 이동(넓히지 않기) |
| 스윙 전환 후보 `SWING_CAND` | 수익 ≥2R + TP1 이후 손절이 본전 이상으로 잠김 + 4h 추세 유지 + 4h 가격>EMA20 + 4h 거래량 ≥0.9배 + 1h 추세 반대 아님 | 잔량 보유 여부를 직접 결정, 추적손절 준수 |
| 스윙 유지 `SWING_HOLD` | 후보 이후 조건 유지, 24시간에 최대 1회 | 추적손절 준수 |
| 스윙 종료 후보 `SWING_END` | 4h 추세 약화 · 가격<4h EMA20 · 수익<1R · 손절 도달 (1회) | 잔량 청산 검토 |
| 일일 손실 한도 | 오늘(KST 00:00~) 실현+평가 손익 ≤ −3% × 오늘 시작 평가액 (1일 1회) | 신규·추가 진입 중단(위험 축소·청산은 가능) |
**손실 포지션·손절 미잠금 포지션은 스윙 후보가 될 수 없다.** 스윙의 수익 개선 효과는 검증되지 않았으며 이 알림은 효과를 주장하지 않는다.

## 4) 위험관리 기준 반영 (최종 지시서)
- 일일 손익 기준: 한국시간 00:00. 실현손익 = 오늘 날짜 체결의 총손익 − 입력된 수수료 + 입력된 펀딩, 미실현 = 열린 포지션의 시세 평가(수수료 제외). 입출금은 손익이 아니므로 반영하지 않는다. 기준 평가액 = 오늘 시작 평가액(장부).
- −3% 도달 시 `ADD_READY` 를 막고 한도 알림을 보낸다. 기존 포지션의 TP/손절/청산 안내는 계속한다.
- 아직 **미반영(4단계)**: 거래당 위험 1%/조건부 1.5% (분할 계획의 현재 기본은 0.5%), 레버리지 3배 이내·총 증거금 30% 상한의 계획 단계 적용, 1.5% 특별 조건. 이번 감시는 계획이 계산해 둔 위험 예산을 그대로 쓰고 새 한도를 만들지 않는다.

## 5) 중복·과다·오래된 신호 방지
- 이벤트마다 dedupe 키(예: `TP1:SID`, `ADD_READY:SID:2`)를 두고 상태에 `sent` 로 기록한다. 같은 키는 다시 보내지 않는다. 포지션이 청산되면 그 상태를 삭제해 알림을 끝낸다.
- **전송 의미: 한 번만(at-most-once)**. 보내기 전에 `pending` 표시를 저장하고, 전송 API가 *실패 응답*을 준 경우에만 같은 본문으로 재시도한다(2·5·10·20분 간격). 전송 직후 프로세스가 중단돼 `pending` 이 남으면 다시 보내지 않는다(드문 누락 가능, 중복은 없음).
- 30분이 지난 실패 알림은 만료시켜 오래된 정보를 보내지 않는다. 한 실행에서 포지션당 최대 3건, 시간당 12건·일 60건 상한(손절 관련 critical 은 상한 제외).
- 트리거 겹침: 사용자 락으로 두 번째 실행은 `busy` 로 즉시 종료. 시세 장애 중에는 전송하지 않는다.

## 6) 성능
감시는 시간 트리거에서만 실행된다(웹앱 요청과 무관). 보유 포지션이 없으면 시세 호출 0. 종목별 1회 `fetchAll`(티커+15m/1h/4h 봉), 봉은 60·150·600초만 캐시하고 현재가는 캐시하지 않는다. 트리거 실행 시간·호출은 `?p=health` 의 "보유 포지션 감시 상태"와 `watch:last` 에 개수로 남긴다(일일 트리거 실행 시간 한도는 실측 후 확인).

## 7) 켜는 순서 (사용자 승인 후, 각각 별도)
1. 코드 배포(새 버전, URL·Deployment ID 유지). 이 상태에서는 아무 동작도 하지 않는다.
2. 편집기에서 `rich300WatchPreview` 실행 → 보유 포지션/이벤트 개수 확인(전송 없음).
3. `RICH300_WATCH_ALERTS=preview` → 트리거 `rich300WatchInstallTrigger()` 설치 → `?p=health` 확인.
4. 실제 Telegram 수신 시험 1건 승인 → `RICH300_WATCH_ALERTS=on`.
끄기: 속성 삭제 또는 `rich300WatchRemoveTrigger()`.

## 8) 한계
- 시세는 OKX/Bybit 공개 가격이라 Binance 체결가·마크가와 다르다. 청산가·마진콜은 계산하지 않는다.
- 거래소 계정과 동기화하지 않는다: 사용자가 체결을 등록하지 않으면 시스템은 그 체결을 모른다.
- 규칙(추세·거래량·스윙)은 백테스트로 우위가 확인된 것이 아니다. 알림은 관리 보조이며 수익을 보장하지 않는다.
