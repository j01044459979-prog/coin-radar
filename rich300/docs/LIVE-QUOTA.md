# Apps Script 할당량·예상 실행 시간 검토와 안전 중단 조건 (24시간 폴링 전 점검)

아래 한도는 **문서상 알려진 값이며 이 프로젝트에서 검증되지 않은 가정**입니다(개인 Google 계정 기준). 그래서 문서상 한도보다 **넉넉한 내부 한도**를 먼저 넘으면 하니스가 스스로 멈춥니다.

## 1. 관련 할당량(가정)
| 항목 | 한도(문서상 가정) | 우리 사용량(추정) | 여유 |
|---|---|---|---|
| 트리거 총 실행 시간 | 90분/일 | 폴링 24~36분 + 마감 ~2분 + 하니스 백그라운드 day-0 약 10~15분 = **약 40~55분** (5분 간격이면 약 15~20분) | 35~50분 |
| 실행 1회 시간 | 6분 | 폴링 1~4초, 마감 수 초, 백그라운드 구간 1~2분(구간별 분리) | 충분(구간을 나눠 한 번에 6분을 넘지 않게 설계) |
| 트리거 개수 | 스크립트·사용자당 20개 | 폴링 1 + 마감 2 + 백업 1 + 일회성 백그라운드 1 = 5 | 충분 |
| UrlFetch 호출 | 20,000/일 | 폴링 1,440(1분 간격) + 메시지 ~100 | 충분 |
| 속성 읽기/쓰기 | 500,000/일, 값 9KB·총 500KB | 폴링당 쓰기 5~8회 ≈ 1만 회/일, 값은 작음 | 충분 |
| 동시 실행 | 30 | 겹침은 사용자 락으로 건너뜀 | 충분 |
| 시간 기반 트리거 간격 | 1·5·10·15·30분 | 1분(예산 초과 예상 시 5분) | — |

## 2. 예상 실행 시간(식)
`하루 예상(분) = 평균 유휴 폴링 ms × (1440 ÷ 간격(분)) ÷ 60,000 + 6(마감·백업·하니스 훅)`
- S0 초기 측정(참고, 카운터 보고값): 최대 3.9초, 729 중 1회 90초 초과 간격 — **실행 횟수로 확정하지 않음**.
- 가정 평균 1초 → 1분 간격 **약 30분/일**, 2.4초 → 약 63.6분(→ 5분 간격 자동 전환), 15초 → 5분 간격도 78분이라 **설치하지 않음**.
- `rich300LiveStart` 가 설치 전에 유휴 폴링 5회를 **직접 측정**해 같은 식으로 간격을 고릅니다(결과는 S0 항목으로 표시).

## 3. 자동 안전 중단(폴링이 끝날 때마다 점검)
중단 = **트리거 제거 + 사유 기록 + `[TEST]` 알림(가능할 때)**. 프로젝트·시트·백업·봇은 삭제·변경하지 않습니다.
| 조건 | 사유 코드 | 비고 |
|---|---|---|
| 환경이 test가 아니거나 운영 승인 플래그가 생김 | `env-guard` | 즉시 |
| 봇 토큰 거부(401) | `bot-token-invalid` | 폐기·오입력 |
| 할당량/호출 한도 오류 감지(예외 메시지 분류) | `quota-exceeded` | 메시지는 저장하지 않고 분류만 |
| 저장소 무결성 문제(30분마다 점검, 마지막 쓰기 중단 흔적은 제외) | `integrity` | |
| 폴링 15회 연속 실패 | `poll-errors` | |
| 폴링 1회 120초 초과 | `run-too-long` | |
| 30초 넘는 폴링 3회 | `slow-runs` | |
| 30회 이상 실행 뒤 하루 예상이 60분 초과 | `runtime-budget` | |
| 하루 메시지 발송 300건 초과 | `message-flood` | |
| 시험 시작 36시간 경과 | `window-ended` | **정상 종료**: 마지막 결과를 보내고 폴링 중단 |
수동 중단: `rich300LiveStop`.

## 4. 이 계획이 하지 않는 것
기존 봇·운영 시트·운영 Secret 접근 없음, 외부 서비스는 Telegram API(테스트 봇)와 Google 서비스만, 자동 주문 없음, 시험 결과 확인 전 삭제 없음(백업 보관 한도 정리로 휴지통에 가는 것은 *시험용 임시 시트 안의 시험 백업*뿐).
