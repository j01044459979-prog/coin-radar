## 2. 같은 봇에서 radar 발송 ↔ 앱 폴링 충돌 점검
| 질문 | 결과 |
|---|---|
| radar 가 getUpdates·웹훅·콜백 응답을 쓰는가 | **아니오.** 모든 브랜치(33개)를 훑어 `getUpdates·setWebhook·deleteWebhook·answerCallbackQuery·callback_query` 사용처가 RICH300 코드 외에 없음. 토큰을 쓰는 곳은 `radar.yml` 하나(발송만). 테스트로도 고정 |
| 발송(sendMessage/sendPhoto)과 폴링(getUpdates)이 서로 막는가 | 아니오. 발송은 언제든 가능, 수신은 getUpdates 소비자 1개만 허용. 앱이 유일한 소비자이면 충돌 없음 |
| 앱이 radar 알림을 건드리는가 | 아니오. 앱은 버튼 응답 후 *그 메시지의 버튼만* 결과 문구로 바꾼다(수정 대상은 사용자가 누른 메시지) |
| 폴링이 다른 소비자와 겹치면 | Telegram 이 409 를 돌려줌 → 앱은 `충돌`로 기록하고 점검 화면 P0 FAIL 로 표시(데이터 손상 없음). 웹훅이 켜져 있어도 같은 409 |
| 허용 업데이트 종류 | 폴링이 `message`·`callback_query` 만 명시해서 요청(이전 설정이 달라도 덮어씀) |
| 첫 폴링에서 쌓여 있던 업데이트 | 최대 50건씩 처리. 페어링 전 사용자의 메시지는 전부 무시·무기록 |

## 3. 기존 웹훅·다른 소비자 확인 방법 (읽기 전용)
- 저장소 정적 점검: 위 2번(완료).
- **`rich300BotCheck()`** (스크립트 속성 `RICH300_TG_READONLY_OK=yes` 필요, `rich300Install` 이 자동 호출): 호출은 **`getMe`·`getWebhookInfo` 두 가지뿐** — 메시지 전송·`getUpdates`(수신 소모)·`setWebhook`·`deleteWebhook` 없음. 승인 게이트가 이 두 메서드 외에는 계속 차단(테스트로 고정).
  - 웹훅 URL 이 있으면 FAIL(다른 수신 서비스 존재, 지우지 않고 멈춤), 대기 업데이트 수·웹훅 오류 기록은 WARN 으로 보고. 값(URL·토큰)은 출력하지 않고 존재 여부·개수만.
- 한계: 웹훅 없이 `getUpdates` 로 동시에 폴링하는 *다른 프로그램*은 그 순간에만 409 로 드러난다(읽기 전용 점검으로는 감지 불가). 승인 후 폴링 시작 뒤 `?p=check` 의 폴링 항목(P0)이 409 를 표시한다.

## 4. '접속한 사용자로 실행 / 나만 접근' 인증 검증 계획
이 조합은 Google 이 소유자 외 접근을 막고, 코드도 접속자 이메일을 소유자와 대조한다(fail-closed). 오프라인으로는 Google 계정 동작을 검증할 수 없어 아래를 실환경에서 한 번에 확인한다(진단 페이지 `?p=ping` 은 값 없이 상태 단어만 출력).
| # | 시험 | 기대 | 판정 |
|---|---|---|---|
| T1 | 소유자 계정으로 `…/exec?p=ping` | `reachable: yes · visitor-email: visible · owner-match: yes · verdict: OK` | OK 면 본인 인증 작동 |
| T2 | 소유자 계정으로 `?p=dash` | 숫자 화면 | 화면이 보이면 서버 소유자 확인 통과 |
| T3 | 다른 Google 계정(시크릿 창 로그인)으로 같은 URL | Google 의 "액세스 권한 필요" 화면(앱 코드에 닿지 않음) | 데이터 노출 없음 |
| T4 | 로그아웃 상태로 같은 URL | Google 로그인 화면 | 데이터 노출 없음 |
| T5 | 코드 쪽 거부 확인(선택) | 이메일이 다르면 `DENY`, 못 읽으면 `BLOCKED`, 둘 다 `?p=dash` 는 빈 응답 | fail-closed |
- T1 이 `BLOCKED`(이메일 못 읽음)이면 **운영 전환 중단**: 화면이 안전하게 막히기만 하고 쓸 수 없는 상태 → 대안(실행 계정·접근 범위 변경 또는 별도 인증)을 정해야 하며 임의로 공개 범위를 넓히지 않는다.
- 이 점검은 데이터를 쓰지 않는다(`ping` 은 읽기 전용, 값 없음).

## 6·7. 사용자 작업 최소화와 설치 자동화 검토
- 현재 사용자 작업: 파일 3개 붙여 넣기 → 속성 2개 → 웹 앱 배포 → 함수 1회 실행 → 확인 URL 2개 열기 → (승인 후) 속성 1개 + 재실행 → 링크 탭. 합쳐서 약 10분, 로그·스크린샷 요청 없음(마지막 `?p=check` 요약 1회).
- 자동화 후보와 판단:
  | 방법 | 줄이는 것 | 필요한 것 | 판단 |
  |---|---|---|---|
  | `clasp`(로컬 CLI)로 push·배포 | 붙여 넣기 3개 | 사용자 PC 에 Node·`clasp login`, Apps Script API 켜기, `clasp` 로는 스크립트 속성(토큰) 설정 불가 | 사용자 PC 작업이 오히려 늘어 비추천 |
  | GitHub Actions 로 자동 push | 붙여 넣기 | Google OAuth 리프레시 토큰을 GitHub Secret 에 저장 | 새 Secret·권한 확대 → 비추천(보안 원칙) |
  | 이 세션에서 Drive 커넥터로 프로젝트 생성 | 붙여 넣기 | 커넥터가 Apps Script 프로젝트 유형 생성을 지원하지 않음(문서·시트·슬라이드·폴더만), 또 사용자 계정 변경이라 미승인 | 불가·미시도 |
  | Code.gs 에 Fill.html 내장(파일 2개로) | 파일 1개 | 코드 수정(작음) | 가능, 다음 개선 후보 |
  | 매니페스트 자동 갱신(스크립트가 Apps Script API 로 자기 설정 수정) | 매니페스트 붙여 넣기 | Apps Script API 토글 + 추가 OAuth 범위 | 권한 확대라 비추천 |
  결론: 안전을 해치지 않는 범위에서는 현재 절차가 최소에 가깝다. 추가로 줄이려면 Fill.html 내장(−1 단계)만 권장.
